# 企业员工档案与人事流程管理平台数据库设计

> 版本：2026-09-17
> 状态：第一阶段开发基线

## 1. 设计范围

平台按核心业务边界拆分为 `identity-service`、`archive-service` 和 `workflow-service`，每个服务只拥有自己的 MySQL 逻辑数据库。`gateway-service` 不持有业务表，`ocr-service` 使用自己的 SQLite 保存任务元数据，并使用 MinIO 保存 OCR 二进制证据。

本设计覆盖：

- 身份、角色、权限、部门和岗位；
- 员工、档案、材料、文件对象和不可变版本；
- OCR 任务关联、检测框预览元数据和字段确认历史；
- 入职、调动、离职、档案访问、审批、借用归还和盘点扩展模型；
- 审计日志、读写分离、缓存和数据保留约束。

## 2. 物理拓扑与读写分离

```text
identity/archive/workflow service
          |                    |
          | write              | @Transactional(readOnly = true)
          v                    v
      MySQL primary ------> MySQL replica
          |
          +----------------> Redis 7
```

- 主库和副本使用 MySQL 8.0、InnoDB、`utf8mb4`。
- 服务通过 `MYSQL_WRITE_URL` 和 `MYSQL_READ_URL` 配置两个连接池。
- 写入、状态迁移、审批、版本发布和写后确认读取使用主库。
- 只读列表、详情和统计事务使用副本；副本延迟或不可用时可降级到主库。
- 路由由公共 `AbstractRoutingDataSource` 实现，业务 Mapper 不感知连接地址。
- 服务之间只传业务 ID 并通过 HTTP 校验，不建立跨库外键。

## 3. 通用规范

- 表名和字段名使用 `snake_case`；时间字段使用 `DATETIME(3)`。
- 核心表使用 `BIGINT UNSIGNED` 主键；ID 只在所属服务内生成。
- 状态使用 `VARCHAR`，由应用状态机校验，避免数据库 ENUM 与服务版本耦合。
- 历史事实不物理删除；使用 `status`、`deleted_at` 或新版本表达撤销和变更。
- 所有核心表包含 `created_at`、`updated_at`；审计表保留操作者、对象、结果和 `trace_id`。
- 身份证号、手机号等敏感字段由应用层加密或脱敏，列表接口禁止返回完整值。
- 文件二进制、OCR 原始 JSON 和检测框 PNG 不进入 MySQL；MySQL 只保存元数据、摘要和业务关联。档案原图和 OCR 效果图由 MinIO 持久化，OCR SQLite 只保存任务 JSON、字段修订和内部对象引用。旧 `OCR_DATA_DIR`/`app/data` 图片目录仅用于迁移。

| `sys_permission` | 权限 | `id`、`code`、`name`、`resource_type`、`status` | `uk_permission_code` |
| `sys_user_role` | 用户角色关系 | `user_id`、`role_id` | 主键 `(user_id, role_id)` |
| `sys_role_permission` | 角色权限关系 | `role_id`、`permission_id` | 主键 `(role_id, permission_id)` |
| `org_department` | 部门树 | `id`、`parent_id`、`code`、`name`、`sort_no`、`status` | `uk_department_code`、`idx_parent_status` |
| `org_position` | 岗位 | `id`、`department_id`、`code`、`name`、`status` | `uk_position_code`、`idx_department_status` |

`employee_id` 和 `leader_user_id` 仅为逻辑引用，不在身份库创建员工表或跨库外键。

## 5. `archive_db`

| 表 | 作用 | 关键字段 | 约束与索引 |
|---|---|---|---|
| `employee` | 员工主数据 | `employee_no`、`name`、`department_id`、`position_id`、`employment_status` | `uk_employee_no`、`idx_department_status`、`idx_name` |
| `archive_record` | 员工档案主记录 | `employee_id`、`archive_no`、`archive_status`、`confidentiality_level` | `uk_employee_id`、`uk_archive_no`、`idx_status` |
| `archive_document` | 档案材料 | `archive_record_id`、`document_type`、`title`、`status` | `idx_archive_type`、`idx_archive_status` |
| `file_object` | 对象存储元数据 | `object_key`、`original_name`、`content_type`、`size_bytes`、`sha256` | `uk_object_key`、`idx_sha256` |
| `archive_version` | 不可变文件版本 | `document_id`、`version_no`、`file_object_id`、`status`、`created_by` | `uk_document_version`、`idx_document_status` |
| `ocr_binding` | 档案版本与 OCR 任务关联 | `version_id`、`ocr_task_id`、`status`、`engine_version`、预览摘要 | `uk_version_ocr`、`uk_ocr_task`、`idx_status_time` |
| `ocr_field_confirmation` | OCR 字段确认历史 | `binding_id`、`field_code`、原始值、确认值、置信度、操作者 | 追加写入；`idx_binding_field_time` |
| `audit_log` | 档案操作记录 | `operator_id`、`action`、`object_type`、`object_id`、前后摘要、`trace_id` | `idx_object_time`、`idx_operator_time` |

`archive_version` 不覆盖历史文件；OCR 结果和字段确认属于证据与确认记录，不能直接覆盖原始 OCR 值。

| 表 | 作用 | 关键字段 | 约束与索引 |
|---|---|---|---|

| `approval_record` | 审批节点历史 | `request_id`、`node_code`、`approver_id`、`decision`、`comment` | `idx_request_node`、`idx_approver_time` |
| `archive_access_application` | 档案访问/借用申请 | `application_no`、`applicant_id`、`target_department_id`、用途、时间范围、`status` | `uk_application_no`、`idx_applicant_status`、`idx_target_department_status`、`idx_expire_status` |
| `archive_access_item` | 申请材料范围 | `application_id`、`archive_document_id`、`archive_version_id`、`scope` | `uk_application_item`、`idx_version` |
| `archive_use_record` | 领取、使用、归还、移交 | `application_id`、领取人、经手人、归还时间、异常说明 | `idx_application_status`、`idx_return_due` |

流程库中的 `employee_id`、`archive_document_id` 和 `archive_version_id` 是逻辑引用。提交、审批、领取和归还前必须调用对应业务服务校验对象存在性、权限和当前状态。

## 7. Redis 数据设计

Redis 不是业务事实库，只保存可重建或短时控制数据：

| Key | TTL | 用途 | 失效策略 |
|---|---:|---|---|
| `hr:perm:user:{id}` | 30 分钟 | 权限摘要 | 角色/权限变更主动删除 |
| `hr:org:department:tree` | 10 分钟 | 部门树 | 部门变更主动删除 |
| `hr:list:archive:{hash}` | 60 秒 | 脱敏档案列表 | 员工/档案写入后删除前缀 |
| `hr:todo:user:{userId}:{sha256(scopeKey)}` | 30 秒 | 当前用户授权范围内的可重建待办摘要 | 按用户和 scope 隔离，过期后回源 |
| `hr:idempotent:{requestId}` | 10 分钟 | 幂等请求占用状态 | 成功结果保留至过期 |
| `hr:lock:{type}:{id}` | <=30 秒 | 发布、归还等互斥 | 必须设置过期时间 |

不缓存身份证原图、完整 OCR JSON、检测框 PNG、文件二进制和不可重建业务事实。

### 7.1 待办查询契约

公共查询接口为 `GET /api/todos?limit=1..100`，由 workflow-service 提供并通过网关访问。成功响应的 `data` 为 `TodoData`，字段为 `items`、`total`、`pendingApprovalCount`、`dueSoonCount`、`overdueCount`、`ocrFailedCount` 和 `generatedAt`。`items` 中的 `TodoItem` 字段为 `id`、`type`、`title`、`resourceId`、`status`、`priority`、`dueAt`、`createdAt` 和 `targetPath`。

`type` 仅允许 `HR_REQUEST_APPROVAL`、`ARCHIVE_ACCESS_APPROVAL`、`ARCHIVE_RETURN_DUE`、`OCR_FAILED`；`priority` 仅允许 `HIGH`、`MEDIUM`、`LOW`。待办 Redis 值仅保存可重建摘要，不能保存 OCR 文件、完整 OCR JSON、检测框 PNG、文件二进制、对象存储 key 或令牌；TTL 固定为 30 秒，key 使用 `hr:todo:user:{userId}:{sha256(scopeKey)}`，scope 必须按用户授权范围隔离。

## 8. 第一阶段落地顺序

1. 保持现有身份库、档案库和读写路由迁移可重复执行。
2. 为部门树和档案列表增加 Redis cache-aside 与事务提交后的失效。
3. 完成 Vue 登录、员工列表、档案上传、OCR 结果和检测框预览页面。
4. 通过网关完成登录到 OCR 预览的端到端验收。
5. 再实现 `workflow_db` 迁移和入职/调动/离职审批闭环。

## 9. 当前迁移与目标模型映射

截至本版本，源码中已经存在并验证的迁移是：

- `identity-service/V1__identity_schema.sql`：身份、角色、权限、部门、岗位和身份审计基础表；
- `identity-service/V2__identity_seed.sql`：初始角色、权限和部门数据；
- `archive-service/V1__archive_schema.sql`：员工、档案记录、材料、文件对象、版本、OCR 绑定、字段确认和档案审计基础表。

源码中已经存在并验证 `workflow-service/V1__workflow_schema.sql`，并通过后续 V2、V3、V4 Flyway 迁移扩展档案访问/使用归还、盘点、异常处理和数据范围快照。目标模型中的字段命名以本设计为准，实施时必须通过新的 Flyway 版本迁移扩展，不能直接修改已应用的迁移文件；每个迁移先由数据库测试验证，再启动对应服务。

## 10. 数据范围与跨服务授权补充

- `identity_db.sys_user.department_id` 由 `V4__user_data_scope.sql` 增加并建立索引；登录签发的 JWT 同时携带 `employeeId` 和 `departmentId`。
- 公共安全模块按角色优先级生成不可变 `DataScope`：管理员为 `ALL`，部门负责人为 `DEPARTMENT`，普通员工为 `EMPLOYEE`，上下文缺失为 `NONE`。
- `archive-service` 的员工列表、版本、OCR 绑定和统计 SQL 均通过 `scopeType`、`employeeId`、`departmentId` 过滤；单资源校验通过后才访问 MinIO 或 OCR 服务。无 scope 的真实 Controller 入口已移除。
- 档案列表缓存 key 仍使用 `hr:list:archive:` 前缀，但摘要输入为 `scopeKey|查询参数`，因此 scope 不同的结果不会互相污染。
- `workflow-service` 保持服务边界，不直接连接其他服务数据库。创建请求、档案访问申请、盘点任务和状态变更使用 JWT 数据范围；员工、材料、版本归属由 archive-service 内部授权 API 校验。`workflow_db` V4 保存目标部门和盘点员工/部门快照，不能使用客户端传入的部门 ID 作为授权依据。

## 10.1 已落地迁移与内部授权边界

- `identity-service/V4__user_data_scope.sql`：为 `sys_user` 增加可为空的 `department_id` 和索引，登录 JWT 携带员工与部门上下文。
- `workflow-service/V2__archive_access_schema.sql`、`V3__inventory_schema.sql`：增加档案访问/使用和盘点业务表。
- `workflow-service/V4__workflow_data_scope.sql`：为人事申请、档案访问申请增加 `target_department_id`，为盘点明细增加 `employee_id`、`department_id` 快照及索引。
- `GET /internal/archive/authorization/employees/{employeeId}`、`GET /internal/archive/authorization/documents/{documentId}` 和 `GET /internal/archive/authorization/versions/{versionId}` 仅供 workflow-service 做归属授权校验；接口复用 archive-service 的 scope-aware SQL，不向 workflow 暴露数据库连接。
- 文件二进制、OCR 原始 JSON 和检测框 PNG 保留在 MinIO/SQLite 的各自边界内；MySQL 只保存预览 URL、内容类型、大小、哈希和尺寸等元数据。

## 11. 材料查询、版本和受控文件读取

`archive-service` 的档案资源工作台复用 `archive_document`、`archive_version` 和 `file_object` 三层模型，不新增表或跨库外键：

- 材料列表通过 `archive_record -> employee` 关联，返回当前材料和最新版本的摘要；版本列表返回版本号、状态、文件名、媒体类型、字节数、SHA-256、创建人和创建时间。
- 材料列表、版本列表和下载查询都必须携带 `DataScope`。部门或员工 scope 不匹配时返回 `403/FORBIDDEN`，不以空列表掩盖单资源越权。
- 下载接口只接收 `versionId`，服务先用 scope-aware SQL 查询版本归属，再用数据库中的 `object_key` 读取对象存储；object key 不由客户端提供，也不写入新接口响应。
- 原始文件内容不进入 MySQL 或 Redis。前端通过受保护接口获取 blob URL，预览或下载结束后释放浏览器对象 URL。
- `VersionData` 的数值字段使用可被 MyBatis JDBC 构造映射稳定处理的包装类型；持久化测试覆盖版本 DTO 构造、跨部门隔离和下载内容。

## 2026-09-20 数据层审核校准

本阶段数据层设计与服务接口契约集中记录于 `docs/superpowers/specs/2026-09-20-microservice-data-contract-design.md`。当前有效规则是：三个 Java 业务服务分别独占逻辑数据库；写入、状态迁移和读己之写使用 MySQL primary，普通查询使用 replica；Redis 只保存权限、部门树、脱敏列表、幂等和短时锁；原图、完整 OCR JSON 和检测框 PNG 不进入 MySQL 或 Redis。

OCR 服务使用自己的 SQLite 与 MinIO 保存原始证据，`ocr_tasks` 的 `source_bucket`、`source_object_key`、`preview_bucket`、`preview_object_key` 和 `storage_version` 是内部字段，不序列化到公开任务 JSON。`archive_db.ocr_binding` 只保存任务关联和检测框预览摘要。任何新增表、字段、索引和 Redis key 必须先补本文件或上述当前规格，再创建新的 Flyway 迁移和对应测试；不得修改已经应用的历史迁移文件。
