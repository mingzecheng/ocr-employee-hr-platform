# 本科毕业设计项目现状评估与优化路线

评估日期：2026-10-12  
评估范围：当前工作区的 Spring Boot、MyBatis、MySQL/Flyway、Vue、PaddleOCR 服务、部署配置、测试和毕业设计材料。  
评估基线：以当前代码和可复现命令为准；旧设计文档只用于说明原计划，不能替代运行证据。

## 1. 结论

当前项目已经从原型阶段进入“可运行的系统骨架”阶段，已覆盖员工、部门负责人、人事管理员和系统管理员四类入口，具备员工档案、档案版本、OCR 识别与人工修订、人事申请审批、档案访问授权、使用/归还/盘点、合同、统计和操作审计等主要模块。

但目前还不能直接作为答辩级最终交付。主要原因不是页面数量不足，而是实现、设计文档和验收证据之间仍有偏差：

1. 当前后端只有一个 MySQL 数据源，没有实现旧设计中承诺的主从读写路由和读写一致性策略。
2. Redis 仅存在依赖和 Compose 配置，当前业务代码没有实际缓存、幂等键或短锁实现。
3. OCR 请求仍在 FastAPI 事件循环中同步执行识别、对象存储和 SQLite 写入，没有并发上限、排队、超时和重试边界。
4. OCR 评测只有一张底图派生的 36 张合成样本，不能支撑真实企业档案泛化结论。
5. 请假审批没有形成“批准→开始生效→结束恢复”的员工状态闭环，OCR 结果也没有受控的正式确认回填动作。
6. 合同续签临近状态在查询时派生，尚未形成可追踪的提醒事件或明确的“只查询、不通知”产品语义。
7. 当前工作区存在大量未提交、删除和未跟踪文件，尚未形成与 GitHub 主分支一致的可复现交付版本。
8. 还没有四种角色从登录到业务闭环的浏览器验收记录，也没有生产等价环境的完整恢复演练证据。

**综合判断：核心系统功能基本成立；数据一致性、技术路线一致性、OCR 实验和交付复现仍需完成后，才能称为完整的本科毕业设计交付。**

## 3. 技术路线与实际实现的偏差

### 3.1 单体后端与旧微服务设计不一致

当前可运行后端是一个 Spring Boot 应用，业务包集中在同一 `server` 模块；OCR 是独立 FastAPI 服务。旧文档中出现过 identity、workflow、archive 等微服务边界，但当前部署和测试应以 `server + ocr-service + MySQL + MinIO` 为准。论文不能同时把项目描述成完整微服务系统和单体系统。

**处理建议：** 将最终架构明确为“模块化单体业务服务 + 独立 OCR 服务”，在论文中解释模块边界、HTTP OCR 契约和拆分理由；删除或标注仅代表未来演进的旧微服务设计。

### 3.2 MySQL 读写分离尚未实现

当前配置只有一个 `spring.datasource.url`，代码中未发现 `AbstractRoutingDataSource`、读库/写库连接池或事务内一致性策略。旧文档中的“主从读写分离”属于设计目标，不是当前能力。

**处理建议：** 本科项目可选择以下一种并写入设计决策：

- 保持单库，删除读写分离承诺，说明演示规模下单库足够；或
- 增加主库/只读库配置、路由数据源、写后读一致性规则和 MySQL 集成测试。

### 3.3 Redis 尚未承担业务职责

项目包含 `spring-boot-starter-data-redis` 和 Redis Compose 服务，但当前业务代码没有缓存、幂等或锁调用。设计文档中关于待办缓存、幂等键和短时锁的描述不能作为实现证据。

**处理建议：** 若保留 Redis，至少实现并测试一个可解释职责，例如待办摘要 cache-aside、重复提交幂等键或审批短锁；若不需要，移除依赖和 Compose 服务，降低部署复杂度。

### 3.4 OCR 是同步任务，不是可恢复任务队列

`async def` 路由不等于后台异步任务。当前识别、预览生成、对象存储和 SQLite 写入在请求处理路径中同步执行，尚未定义最大并发、单任务超时、失败重试、重复上传幂等和服务重启后的处理中间态恢复。

**处理建议：** 本科演示可以继续单进程同步处理，但必须写明容量边界并增加超时、并发限制和失败状态；若需要论文中强调可靠处理，再引入轻量任务队列或进程池，并保留任务状态机。

### 3.5 人事状态和 OCR 结果的业务落点不完整

入职、调动和离职已经有员工变更执行逻辑，但请假申请没有对应的开始/结束状态转换；OCR 已有识别、映射、校验和人工修订，但修订结果没有通过一个明确的确认动作进入员工档案或申请正式字段。合同续签窗口同样只是列表查询时的派生值，不是独立的待办事件。

**处理建议：** 先固定三个跨模块契约：员工状态机必须定义请假生效与恢复；OCR 必须定义待确认、已确认、拒绝和来源版本；合同必须明确查询派生与主动提醒的边界。再据此补迁移、服务、页面、审计和验收测试，避免仅增加按钮而没有真实状态落库。

## 5. 主要不足与验收标准

### P0：交付前必须关闭

1. **交付版本不可复现**

   - 证据：`git status` 显示大量修改、删除和未跟踪文件，当前评估依赖工作区而非稳定提交。
   - 风险：评审者从 GitHub 克隆后无法得到同一系统，测试和演示证据无法复核。
   - 动作：整理实现、迁移、文档和前端产物；删除无关生成文件；提交稳定版本；从干净克隆执行部署和测试。
   - 验收：新目录中只用 README 命令即可从空库启动；GitHub commit、镜像/构建版本和评估文档一致。

2. **架构承诺与代码不一致**

   - 证据：单一 `spring.datasource.url`，没有路由数据源；Redis 无业务调用；旧文档仍描述主从和缓存。
   - 风险：论文、答辩和实际系统对技术路线的陈述互相矛盾。
   - 动作：在单库/读写分离和 Redis 是否保留之间作出正式决策，并同步代码、配置、部署、论文和 API 文档。
   - 验收：架构图、README、配置和测试对数据库、Redis、OCR 的职责完全一致；没有“已实现但代码不存在”的描述。

3. **敏感档案授权矩阵不完整**

   - 证据：内容入口已有无授权拒绝测试，但真实 MySQL 状态组合未覆盖全量。
   - 风险：待审、已归还、过期或异常状态可能出现元数据可见但内容越权，或应允许读取却被错误拒绝。
   - 动作：以本人、部门负责人、HR、管理员为维度，覆盖待审、批准、驳回、过期、使用中、归还、异常未关闭和异常关闭；同时测试下载、OCR 结果、预览、触发和修订。
   - 验收：每个状态和角色均有正向/负向 MySQL 测试，统一使用同一授权策略，测试结果归档。

4. **核心关系完整性和历史语义未定稿**

   - 证据：`sys_user.employee_id`、`sys_user.department_id` 只有索引，不是外键；历史版本、合同、OCR 修订和授权的跨表语义尚未集中说明。
   - 风险：账号绑定员工被删除或迁移后可能出现悬挂关系；旧版本是否可读、修订是否追溯不清。
   - 动作：决定采用外键、归档禁止删除或服务层约束；明确当前/历史版本授权、OCR 修订、合同来源和盘点记录的读取规则。
   - 验收：ER 图、迁移 SQL、API 文档和 MySQL 测试对同一关系给出一致答案。

5. **OCR 任务可靠性没有边界**

   - 证据：同步 OCR、对象存储和 SQLite 操作在请求路径内，没有队列、超时、并发上限和重试策略。
   - 风险：大图或并发上传会阻塞服务；中途失败可能留下不完整对象或任务状态。
   - 动作：至少增加文件处理超时、最大并发、失败状态、重复 task 幂等和启动后处理中任务策略；按演示规模记录容量边界。
   - 验收：并发压测、OCR 超时、对象存储失败、进程重启和重复请求均能得到稳定状态和可重试结果。

6. **请假审批没有完整的状态生效闭环**

   - 证据：`EmployeeChangeService.applyEmployeeChange` 的生效日期分支只处理 `ONBOARDING`、`TRANSFER` 和 `OFFBOARDING`；`LEAVE` 走默认分支并保留原员工状态，当前没有请假开始进入 `ON_LEAVE`、结束恢复 `ACTIVE` 的定时或补偿逻辑。
   - 风险：已批准且已开始的请假仍显示为在职，部门范围、统计、调动/离职校验和待办判断可能与实际业务状态不一致。
   - 动作：将请假拆成批准、开始生效、结束恢复三个可审计状态；增加日期边界、重复请假、跨日和服务重启后的补偿执行规则。请假期间是否允许发起离职、调动和档案借用也要写入状态机规则。
   - 验收：批准前、请假开始日、请假结束日和补偿执行后分别有员工状态、状态历史、统计和权限的 MySQL 测试；重复执行不能重复写历史。

7. **OCR 识别结果不能正式确认回填**

   - 证据：当前后端提供查询 OCR 结果和按字段人工修订接口，但没有将“已修订且通过校验”的结果确认写入员工档案或人事申请正式字段的接口，也没有确认人、确认时间和来源版本的统一状态。
   - 风险：OCR 结果停留在识别附件中，演示无法证明智能识别真正减少了档案录入；若前端自行覆盖正式字段，还会绕过权限、校验和审计。
   - 动作：增加待确认/已确认状态和受控确认接口，明确可回填字段白名单、字段格式校验、冲突处理、操作者权限以及“变更前/变更后/来源 OCR 版本”的审计摘要；正式档案不得被低置信度或未修订的结果直接覆盖。
   - 验收：同一结果重复确认幂等；低置信度或无效格式不能确认；确认后员工档案/申请详情可读到来源版本；审计日志包含操作者、时间、前后值和任务号。

### P1：决定论文质量和答辩完整度

8. **OCR 实验样本不足**：36 张由同一底图派生的合成图仅覆盖姓名和员工编号。需要多版式、扫描/拍摄、旋转、阴影、模糊、遮挡和更多业务字段，并保存脱敏真值、样本哈希和标注规则。

9. **OCR 指标不完整**：除字段准确率外，应报告检出率、失败率、错误类别、置信度分层、低置信度召回率、人工修订率和 P50/P95 延迟，并区分 OCR 识别错误与业务字段映射错误。

10. **权限模型双重来源**：数据库中有 `sys_permission` 和 `sys_role_permission`，接口执行主要依赖硬编码角色注解。需选择固定角色模型或实现数据库驱动权限，不能让管理员页面暗示动态权限已生效。

11. **统计口径不够可复算**：已有概览、趋势、部门和流程周期，但需要定义统计时区、起止日期是否包含、无数据返回、权限范围、取消/驳回是否计入，以及 SQL 或导出结果如何复算。

12. **数字档案和纸质档案边界不清**：当前对象是 MinIO 中的数字文件和版本。若任务书的借用、归还、盘点指纸质实物，应补柜、盒、位置、实体交接和损毁模型；若只做数字档案，应在需求和论文中明确排除实物管理。

13. **合同到期只在查询时派生状态**：`ContractService` 根据当前日期把 `NOT_DUE` 映射为 `DUE`，但没有独立的到期提醒待办、通知记录或定时持久化状态。若用户不打开合同列表，系统没有可追踪的提醒事件。
   - 动作：选择“查询派生且明确不承诺通知”或增加合同提醒任务表/待办事件、幂等键和已读/处理状态；在论文中统一口径。
   - 验收：时间跨过提醒窗口后，指定角色可在待办中心看到稳定的提醒，并能查看来源合同、处理结果和审计记录；重复调度不重复生成事件。

14. **生产恢复缺实战证据**：已有加密备份、恢复脚本和静态审查，但未在生产等价环境完成数据库、MinIO、OCR SQLite 的一致性恢复以及恢复后的业务读写验收。

15. **论文和参考文献未定稿**：需要把现有文档转成需求分析、总体设计、详细设计、数据库设计、OCR 算法/实验、系统测试、结论与局限；任务书附带的宠物店系统文献不能直接作为本课题最终参考文献。

### P2：质量提升和演示完善

16. 建立跨角色异常矩阵：重复提交、重复归还、并发审批、离职交接未完成、盘点异常未关闭、OCR 不可用、对象存储不可用。

17. 增加历史档案时间线，明确版本、OCR 修订、授权决定、使用/归还、合同和员工状态变更的关联顺序。

18. 审查失败路径日志，确保保留 traceId 和稳定错误码，但不写入姓名、手机号、原图文本、私有对象 key 或完整 OCR JSON。

19. 在干净机器验证镜像构建、密钥检查、迁移启动顺序、OCR 模型准备、对象存储权限、健康检查、备份和关停脚本。

## 6. 优化顺序

### 阶段 0：固定评估基线和交付版本

1. 固定 Java 17、Node 版本、Python/OCR 运行时和模型版本。
2. 清理并提交当前实现，确保 GitHub 与工作区一致。
3. 从空 MySQL、空 MinIO 和空 OCR 数据目录启动一次，保存命令、版本、健康检查和截图。

**退出条件：** 干净克隆可以构建、迁移、启动和执行演示；文档中的命令与实际目录一致。

### 阶段 1：统一架构、权限和数据不变量

1. 决定单库还是读写分离，决定 Redis 是否承担真实职责。
2. 完成档案内容授权全矩阵，覆盖所有内容入口和状态。
3. 解决账号与员工/部门关系的外键或替代约束。
4. 统一数据库权限表、角色注解、管理员页面和论文中的权限模型。
5. 定稿请假状态机和 OCR 结果确认回填的正式数据边界。

**退出条件：** 架构文档不再描述不存在的能力；敏感内容不存在越权读取；关系和状态机在 MySQL 上可验证。

### 阶段 2：补 MySQL 组合行为和业务异常验收

1. 为核心 mapper 增加日期、JSON、唯一约束、外键、乐观锁和稳定分页排序测试。
2. 覆盖人事申请（含请假开始/结束）、OCR 确认回填、档案授权、归还、盘点异常、合同提醒和统计的正常与冲突路径。
3. 为员工、部门负责人、HR、系统管理员执行浏览器端到端脚本。

**退出条件：** 核心业务不依赖 H2 特有行为，四角色可完成最小闭环和异常闭环。

### 阶段 3：完善 OCR 可靠性与论文实验

1. 增加 OCR 任务超时、并发限制、失败状态和幂等/重试策略。
2. 建立多版式脱敏样本集和人工标注规范。
3. 一条命令生成准确率、召回率、失败类别、修订率和延迟统计，并保存原始 JSON。

**退出条件：** OCR 实验可重放，结论限定在实际样本范围内；服务不可用和重复请求有稳定处理结果。

### 阶段 4：完成运维和论文交付

1. 在隔离生产等价环境完成加密备份、对象文件校验、恢复和业务读写验收。
2. 完成论文正文、参考文献核验、图表编号、测试报告和答辩脚本。
3. 将所有关键数字链接到测试报告、实验原始结果或数据库查询。

**退出条件：** 答辩演示不依赖开发者个人数据库状态，论文结论和 GitHub 版本可复核。
