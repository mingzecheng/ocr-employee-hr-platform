## 需求概述

本课题拟建设一个面向企业员工、业务经办人员、部门负责人和人事运营管理人员的员工档案与人事流程管理平台。平台以员工档案材料为核心资源，覆盖建档、申请授权、使用或借用、审批、变更维护、归还移交、盘点异常和归档统计等环节，同时覆盖入职、转岗调动、请假异动、合同和离职交接等典型人事流程。OCR 是系统的核心智能化功能，负责从扫描件或图片中提取关键字段，并直接返回文本、字段、坐标、置信度和自动校验结果。

本课题的重点不是做一个通用 OCR 模型，而是验证“档案业务流程 + 文档字段抽取 + 全程留痕”的完整业务闭环。建议将员工档案材料定义为系统中的主要资源对象，避免将题目扩展成泛化的资产借还系统。

## 使用角色与场景

| 角色 | 主要职责 |
|------|----------|
| 员工/业务经办人员 | 查看本人或职责范围内档案，发起入职、调动、请假、离职及档案访问申请，上传材料并处理待补正项 |
| 部门负责人 | 审批本部门员工的人事申请、档案访问和借用申请，查看必要的部门统计 |
| 人事/运营管理人员 | 维护员工、组织和岗位，管理档案材料、OCR 结果、合同、盘点、归档和异常，执行最终审核 |
| 系统管理员 | 维护账号、角色、权限和基础字典；可与人事运营角色合并，以控制毕设规模 |

## 核心业务闭环

资源建档 → 申请访问或借用 → 权限审批 → 分配使用 → 版本变更或维护 → 归还/移交 → 盘点与异常处理 → 归档统计。

每一次关键操作都应关联操作者、时间、业务单据、对象版本和变更前后内容。审批拒绝、撤回、超期、缺件、识别失败和人工修正都应有明确状态和操作记录。

## 功能需求

### P0 - 必须实现

- [ ] 身份认证与角色权限：支持登录、退出、密码校验、角色分配和菜单/接口级权限控制。
- [ ] 组织与员工基础数据：维护部门、岗位、员工及其在职状态，支持员工与部门、岗位的真实关联。
- [ ] 员工档案资源建档：维护档案分类、材料清单、原图附件、当前版本、保管状态和归档状态。
- [ ] 档案访问/借用申请：记录申请人、申请目的、资源范围、使用方式、起止时间和归还要求。
- [ ] 审批流程：支持经办人员提交、部门负责人审批、人事人员复核，记录审批意见、时间和结果。
- [ ] 使用、归还和移交：记录领取人、经手人、归还时间、移交对象、缺件/损坏情况和超期状态。
- [ ] 变更与版本留痕：档案材料替换、字段修订和状态变更不得直接覆盖历史，应保存版本、来源和变更说明。
- [ ] 人事流程：至少实现入职、转岗/调动、请假异动、离职交接中的三类典型流程，包含表单、审批和状态流转。
- [ ] OCR 信息抽取：支持只上传扫描件或图片，完成图像预处理、文字识别、字段映射、自动格式校验，并直接返回结果。
- [ ] OCR 原始证据：保留原图、识别结果、字段置信度、字段来源位置和 OCR 引擎版本。
- [ ] 检索与分页：按员工、部门、档案分类、流程状态、申请人和时间范围组合查询，列表支持分页、排序和权限过滤。
- [ ] 操作日志与异常处理：记录登录、上传、审批、下载、借用、归还、修改和权限变更等操作，提供失败、撤回、驳回和异常状态。

### P1 - 重要功能

- [ ] 合同管理：记录合同类型、签署日期、起止日期、续签状态和关联员工，合同文件作为档案版本管理。
- [ ] 盘点任务：按部门或档案分类发起盘点，记录实际状态、缺失项、异常说明和处理结果。
- [ ] 人事统计可视化：展示员工数量、部门分布、入离职趋势、流程数量、档案完整率、OCR 识别准确率和失败率。
- [ ] 批量导入和导出：支持脱敏员工基础数据或档案清单的模板导入，导出结果必须受权限控制并留下日志。
- [ ] 待办提醒：对待审批、待归还、即将到期和 OCR 失败的事项提供列表或站内提醒。

### P2 - 可选功能

- [ ] 针对固定表单的小样本微调实验，并与通用预训练模型进行对比。
- [ ] 文档相似度或重复材料检测。
- [ ] 消息推送、电子签名、真实企业单点登录和移动端适配。

## OCR 需求边界

建议首期只选择 3 类左右版式相对稳定且业务价值明确的材料作为演示对象，例如入职登记表、员工异动申请表和离职交接表。每类材料定义字段模板，如姓名、员工编号、原部门、新部门、生效日期、申请原因、审批人和日期等。

OCR 输出是接口直接返回的识别结果。OCR 接口不要求人工确认；业务系统是否将结果写入员工、岗位或流程单据，由上层业务流程自行决定。识别失败时仍保存原图和错误信息，不能因 OCR 失败导致接口异常丢失源文件。

## 非功能需求

- 性能：普通图片上传后应能看到任务状态；单张常规扫描件的识别结果应在可接受时间内返回，耗时应被记录而不是写死为固定承诺。查询接口应支持分页，避免一次性加载全部档案。
- 安全：采用最小权限原则；员工只能访问本人或被授权的数据，部门负责人只能访问职责范围内数据，人事人员按岗位授权。敏感字段、原图和下载行为应纳入日志。
- 数据保护：使用模拟或脱敏数据，不收集与员工档案和流程无关的信息；原图、OCR 结果和修订记录分开保存并可追溯。
- 一致性：审批、借用、归还、版本发布和归档等状态变更应在事务中完成，避免出现审批已通过但资源未分配的半成功状态。
- 可维护性：OCR 引擎、字段模板、校验规则和业务系统解耦，支持替换 OCR 组件而不重写业务模块。
- 可测试性：核心接口、权限边界、状态流转、异常流程和 OCR 评测应有可复现测试数据。

## 边界与约束

- 不做从零训练通用 OCR 模型，不把模型训练本身作为系统上线的前置条件。
- 不接入真实企业 HR、社保、薪资或电子签名系统；使用模拟数据或脱敏样例完成演示。
- 不实现复杂的多级流程编排平台；审批节点固定为经办人提交、部门负责人审批、人事复核即可满足毕设展示。
- 不把所有可能的人事制度都做成配置项，优先保证 3 类典型单据和一条完整闭环。
- “借用”同时可表示纸质档案借阅和数字档案访问。系统应通过 `use_type` 区分，若时间有限可以先完成数字访问授权，保留借还字段。

## 验收标准

### 认证与权限

- Given 一个拥有不同角色的测试账号，When 访问不属于其权限范围的员工档案，Then 接口返回无权访问且前端不展示受限数据。
- Given 用户登录成功，When 执行新增、审批、下载或权限变更，Then 操作日志记录用户、对象、时间、结果和必要的请求标识。

### 档案闭环

- Given 一份新上传的员工档案材料，When 人事人员完成建档并提交访问申请，Then 系统生成申请单并进入待审批状态。
- Given 部门负责人审批通过，When 经办人员使用并归还材料，Then 系统记录使用起止时间、归还/移交对象和资源当前状态。
- Given 已归档材料发生替换或修订，When 人事人员发布新版本，Then 旧版本仍可查询，新版本具有来源、操作者和变更说明。
- Given 归还时发现缺件或损坏，When 操作人员提交异常，Then 系统将资源标记为异常并生成待处理记录，不得直接进入正常归档状态。

### OCR 闭环

- Given 一张扫描件或图片，When 用户上传并启动 OCR，Then 系统生成任务并返回文本、字段、字段来源位置、置信度和自动校验结果。
- Given 字段置信度较低或格式校验失败，When OCR 任务完成，Then 接口仍直接返回该字段的识别值、置信度、位置和自动校验状态，不等待人工确认。
- Given 用户上传图片，When OCR 模型识别成功，Then 接口返回 `SUCCEEDED` 状态和完整识别结果。
- Given OCR 引擎不可用或识别失败，When 任务结束，Then 系统保留原图、错误信息和失败状态，调用方可以根据失败结果自行处理。

### 评测与统计

- Given 按高、中、低清晰度分组的脱敏样本和人工标注真值，When 运行评测，Then 系统输出字段级准确率、字符级相似度、失败数、低置信度数和平均耗时。
- Given 统计查询条件和用户权限，When 查询统计数据，Then 结果只包含授权范围内数据，并支持按时间、部门或文档类型筛选。

## 待确认假设

- 未提供既有技术栈，方案默认采用 Vue 3 + Spring Boot + MySQL，并将 Python OCR 服务独立部署。
- 若指导老师要求单体部署，可将 OCR 调用封装为同机进程或命令调用，但建议保留统一 HTTP 接口，便于论文展示模块边界。
- 字段识别准确率的最终目标应以实际样本和标注结果为准，不能只引用 OCR 引擎宣传指标。

## OCR 流程调整

根据当前实现要求，OCR 首期流程调整为“上传图片 → 模型识别 → 直接返回结果”。成功任务状态为 `SUCCEEDED`，识别字段通过 `value` 返回，置信度、坐标和自动规则校验结果一并返回；不再设置人工校验、人工修订或复核接口。识别失败时任务状态为 `FAILED`，保留原图和错误信息，便于调用方处理失败结果。

## 2026-09-16 OCR 当前验收补充

当前本地 OCR 服务在同步返回识别结果的基础上，已提供低置信度/校验失败标记、人工字段修订及修订历史。人工修订不会改变原始 OCR 文本块，只更新字段的人工确认值并重新执行规则校验，满足“原图、原始识别值、修订留痕分离”的要求。

针对与主业务平台的边界，OCR 服务只产生和查询 `taskId` 对应的识别证据；员工、档案版本、人事申请、审批和授权关系由业务后端维护，并使用 `taskId` 进行关联。这样 OCR 失败时仍可保留原图和失败信息，业务流程可以转人工录入，不因模型失败丢失档案材料或中断审批。

评测接口接受高、中、低清晰度脱敏样本的即时人工真值，输出字段准确率、字段检出率、失败率和平均处理耗时。真值不写入 SQLite，避免为评测目的额外保存不必要的员工个人信息。

## 2026-09-17 系统项目当前需求基线

### 需求概述

本项目建设企业员工档案与人事流程管理平台，采用核心业务微服务架构。平台以员工、员工档案材料和人事流程为主要业务对象，覆盖身份认证、组织与员工维护、档案建档、材料版本管理、OCR 识别、访问/借用申请、审批、使用归还、盘点异常和统计审计。前端使用 Vue，业务后端使用 Spring Boot + MyBatis，业务数据使用 MySQL，缓存使用 Redis，OCR 继续复用已经完成的独立 Python FastAPI + PaddleOCR 服务。

本版需求是后续数据库设计、服务工程和接口实现的审核基线。它覆盖完整 P0 业务闭环，但代码实现按可独立验收的阶段推进，不在第一批代码中一次性实现所有 P1 功能。

### 使用角色

| 角色 | 主要职责 | 数据范围 |
|------|----------|----------|
| 员工/业务经办人员 | 查看授权范围内材料，发起人事申请和档案使用申请，上传业务材料 | 本人或被授权资源 |
| 部门负责人 | 审批本部门人事和档案使用申请，查看部门范围统计 | 本部门 |
| 人事/档案管理员 | 维护员工、档案、材料版本，复核 OCR 字段，处理归还、盘点和异常 | 全组织或被授权组织 |
| 系统管理员 | 用户、角色、权限、部门和系统配置维护 | 系统管理范围 |

### 首期 P0 功能

- [ ] 认证与权限：登录、退出、JWT 校验、角色/权限分配、菜单权限和接口权限。
- [ ] 组织与员工：部门树、岗位、员工编号唯一性、在职状态、入离职日期和部门/岗位关联。
- [ ] 档案建档：员工档案主记录、材料分类、保密级别、材料完整性、档案状态和权限范围。
- [ ] 文件与版本：原图文件元数据、文件哈希、材料版本、当前版本、来源和变更说明；历史版本只读保留。
- [ ] OCR 对接：上传图片后调用独立 OCR 服务，保存 `taskId` 关联、原始识别结果摘要、字段确认结果和检测框效果图地址。
- [ ] OCR 复核：展示文本框、置信度、自动校验结果和效果图；支持字段人工修订且保留修订历史，原始 OCR 结果不可覆盖。
- [ ] 人事流程：首期实现入职、调动和离职交接三类流程；请假异动保留同一流程模型的扩展能力。
- [ ] 档案访问/借用：申请、部门审批、人事复核、授权、使用、归还/移交和超期异常。
- [ ] 盘点与异常：按档案材料发起盘点，记录缺失、损坏、位置不符和处理结论。
- [ ] 检索与统计：员工、部门、材料、流程、OCR 任务分页查询，以及档案完整率、流程数量和 OCR 运行指标。
- [ ] 审计：登录、下载、上传、识别、修订、审批、授权、归还、盘点和权限变更记录操作人、对象、时间、结果和 traceId。

### P1/P2 范围

- P1：合同管理、批量导入/导出、待办提醒、部门和时间维度统计看板。
- P2：固定表单小样本微调、文档重复检测、真实企业系统或移动端适配。

### OCR 对接边界

业务平台不直接依赖 OCR 服务的 SQLite 数据库，也不把 OCR 原始结果直接覆盖到员工主数据。档案服务通过 HTTP 调用以下现有接口：

1. `POST /api/ocr/tasks`：上传 PNG/JPEG，接收同步识别结果和 `taskId`。
2. `GET /api/ocr/tasks/{taskId}`：查询原图元数据、文本块、字段、置信度和任务状态。
3. `GET /api/ocr/tasks/{taskId}/detection-preview`：获取保存的检测框效果图；历史任务支持按需补生成。
4. `PUT /api/ocr/tasks/{taskId}/fields/{fieldCode}`：提交字段人工修订并保留修订记录。

业务侧至少保存 OCR 任务关联、档案版本关联、确认人、确认时间、发布结果、检测框 URL/哈希和错误状态。`DETECTION_PREVIEW_NOT_FOUND` 只表示效果图证据缺失，不能被业务侧误判成 OCR 识别失败；前端应允许重新请求并展示原图和原始文本结果。

### 非功能需求

- 一致性：同一业务写事务使用 MySQL 主库；状态变更、版本发布、审批通过和归还操作不得只修改单个状态字段而不记录历史。
- 读写分离：查询默认走只读副本，写入和需要读己之写的查询走主库；服务应记录副本延迟和路由结果。
- 缓存：Redis 只缓存可重建数据、会话、权限、字典、列表摘要和幂等状态，不缓存原图、检测框 PNG 或完整 OCR 原始证据。
- 安全：JWT、最小权限、敏感字段脱敏/加密、下载权限校验、文件类型和大小校验、审计日志。
- 可用性：OCR 失败保留原图并允许人工录入；Redis 或只读副本不可用时不得破坏主库写入，查询降级行为必须有日志。
- 可追溯：文件以 SHA-256 校验，OCR 保存引擎版本和耗时，档案版本、字段修订和审批记录不可物理覆盖。

### 业务闭环验收标准

1. Given 管理员已创建部门、岗位和用户，When 用户登录，Then 认证服务返回 JWT，网关和业务服务均能校验角色与数据范围。
2. Given 人事管理员上传员工档案材料，When 档案服务保存文件并调用 OCR，Then 返回档案版本、OCR `taskId`、文本块、字段、置信度和检测框预览信息。
3. Given OCR 结果字段置信度低或格式校验失败，When 人事人员修订字段，Then 原始识别值仍可查询，修订值、原因、操作者和时间可追溯。
4. Given 申请人提交档案访问申请，When 部门负责人和人事人员依次审批，Then 申请状态按状态机流转，授权范围和审批意见完整保存。
5. Given 已授权材料被使用，When 操作人员归还并发现缺件，Then 使用记录保存归还信息，档案或材料进入异常状态并生成异常记录。
6. Given 同一材料存在历史版本，When 发布新版本，Then 旧版本只读保留，新版本成为当前版本，且所有版本均能关联文件哈希、上传人和来源。
7. Given 读副本存在复制延迟，When 请求刚写入的数据，Then 命令响应和读己之写请求使用主库，普通列表查询仍可按策略使用读副本。

### 明确不做

- 不从零训练通用 OCR 模型，不接入真实社保、薪资、电子签名或企业 HR 系统。
- 不建设通用流程编排引擎，首期固定“提交—部门审批—人事复核”节点。
- 不在服务之间建立跨库物理外键，不允许业务服务直接读取其他服务数据库。
- 不将原图、检测框效果图和完整 OCR 原始 JSON 放入 Redis。

## 2026-09-18 数据范围权限验收补充

数据范围权限已从接口级授权细化到档案业务数据和统计聚合：

- `SYSTEM_ADMIN`/`HR_ADMIN` 使用全组织范围；`DEPT_MANAGER` 使用 JWT 中的 `departmentId`；普通员工使用 JWT 中的 `employeeId`；缺少必要上下文时使用空范围，不扩大权限。
- 员工列表、档案版本、OCR 绑定、OCR 结果、检测框预览、字段修订和统计查询均在 SQL 或单资源查询中应用数据范围。
- 员工列表 Redis key 的摘要输入包含 scope 指纹，避免不同用户复用列表缓存。
- 跨范围资源在读取对象存储或调用 OCR 前返回 `403/FORBIDDEN`；检测框预览缺失仍与 OCR 文字识别结果解耦。

workflow-service 仍只保存业务库内的员工和档案逻辑 ID，不跨库读取 archive/identity 表，也不接受客户端提交的部门范围作为授权依据。当前已通过 archive-service 内部授权 API 校验员工、档案材料和档案版本归属，并在 workflow_db 保存 `target_department_id` 及盘点明细的员工/部门快照；流程、访问申请和盘点查询/变更均使用 JWT 数据范围过滤。

## 2026-09-20 微服务项目开发基线校准

本阶段以 `docs/superpowers/specs/2026-09-20-microservice-data-contract-design.md` 为当前审核对象。项目继续沿用现有核心微服务，不重建工程：`gateway-service` 负责统一入口，`identity-service` 管理身份与组织，`archive-service` 管理档案与 OCR 业务绑定，`workflow-service` 管理人事流程、档案访问和盘点，独立 `ocr-service` 负责图像文本识别与原始证据保存。

数据库按服务划分为 `identity_db`、`archive_db`、`workflow_db`，采用 MySQL 主从读写分离；Redis 只保存可重建缓存、幂等标记和短时锁。前端只访问网关，服务之间只通过 HTTP 和业务 ID 对接，不跨库读取或建立跨库外键。代码开发须在该规格和实施计划审核通过后继续。
