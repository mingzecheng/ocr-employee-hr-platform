## 技术方案概述

采用“模块化单体业务系统 + 独立本地 OCR 服务”的架构。业务系统负责认证、权限、员工和档案关系、流程状态、审批、版本、日志和统计；OCR 服务负责图像预处理、文字识别、版面分析、字段映射和置信度计算。两者通过内部 HTTP API 通信，OCR 服务使用成熟的中文 OCR 预训练模型，不从零训练通用模型。这样既能满足本地数据处理和毕设的可解释性，又能让 OCR 引擎与业务代码解耦。

## OCR 方案结论

推荐方案：本地部署 PaddleOCR，并以 PP-Structure 系列能力处理版面、表格和文字，再由服务完成字段映射和自动格式校验后直接返回结果。具体版本应在实现时锁定并记录，避免论文中只写“调用 OCR”。

不建议把“从零训练 OCR 模型”作为主方案，原因是：

1. 题目核心是人事档案业务闭环，通用文字检测和识别不是主要创新点。
2. 从零训练需要大量标注图片、检测框和识别文本，训练成本高，且容易把时间耗在数据集和模型调参上。
3. 员工档案中最难的问题通常是版面、字段语义、表格定位、格式校验和人工纠错，单纯提升字符识别模型不能解决完整业务问题。

推荐的 OCR 管道如下：

```text
上传原图
  -> 文件类型/大小/病毒与哈希校验
  -> 方向检测、裁剪、去噪、二值化、倾斜校正、分辨率统一
  -> 文字检测 + 中文识别 + 版面/表格分析
  -> 按 document_type 选择字段模板
  -> 字段定位、值归一化、格式校验、置信度分级
  -> 直接返回识别结果
```

字段结果至少包含 `field_code`、`value`、`confidence`、`bbox`、`page_no` 和 `validation_status`。原图只读保存，识别结果与原图元数据关联保存。

置信度用于向调用方说明模型结果的可靠程度，自动格式校验用于标记可能存在问题的字段，但二者都不阻塞接口返回。最终论文中应通过实验报告不同清晰度和文档类型下的识别效果，不能只引用模型宣传指标。

## OCR 评测设计

准备按高、中、低清晰度分组的脱敏样本，并制作人工标注真值。每种表单至少覆盖正常样本、倾斜、模糊、阴影、印章遮挡、手写或缺失字段等情况。训练集、验证集和测试集按原始文件划分，避免同一张表单的不同处理版本泄漏到不同集合。

建议统计：

- 字段准确率：归一化后预测值与真值完全一致的字段比例。
- 字符级相似度：用于姓名、地址、原因等长文本字段。
- 检出率：应识别字段中成功返回结果的比例。
- 低置信度率：低于设定置信度阈值的字段比例，用于评估模型输出风险。
- 失败率和平均耗时：按文档类型、清晰度和引擎版本统计。

论文中应报告引擎原始结果、自动校验结果和接口耗时，区分模型识别能力与规则标记能力。

## OCR 接口实现调整

首期本地 OCR 服务采用同步识别模式：客户端上传图片后，接口直接调用当前 OCR 引擎并在同一响应中返回识别文本、字段值、坐标、置信度和自动校验结果。识别成功后任务状态为 `SUCCEEDED`，不再进入 `REVIEW_REQUIRED` 或 `CONFIRMED`，也不提供人工复核接口。识别失败时返回 `FAILED` 任务，同时保留原图和错误信息。

当前接口为：

- `POST /api/ocr/tasks`：上传图片并直接返回识别结果。
- `GET /api/ocr/tasks/{taskId}`：查询已经保存的任务结果。

字段结果使用 `value` 保存模型识别值；`validationStatus` 仅表示自动规则校验状态，不会阻塞结果返回。

## 2026-09-16 OCR 服务当前对接契约

本地 Python OCR 服务位于 `ocr-service`，使用 PaddleOCR 作为默认引擎。它只负责保存 OCR 原始证据和返回可追溯的识别结果，不直接写入员工、档案版本或人事流程主数据；业务后端应以 `taskId` 关联 `archive_version`、流程单据或人工确认后的业务字段，避免 OCR 原始值直接覆盖主数据。

### 已实现接口

- `POST /api/ocr/tasks`：上传 PNG/JPEG 图片，同步返回 OCR 任务；传入 `documentType=employee_profile` 时映射员工姓名、员工编号、身份证号和手机号。
- `GET /api/ocr/tasks/{taskId}`：查询原图元数据、文本块、字段、置信度、坐标、处理耗时和失败状态。
- `GET /api/ocr/tasks?page=1&pageSize=20`：按创建时间倒序查询持久化任务，供档案或流程列表关联展示。
- `PUT /api/ocr/tasks/{taskId}/fields/{fieldCode}`：提交人工修订，重新校验格式并保存不可变修订记录。
- `GET /api/ocr/tasks/{taskId}/field-revisions`：查询人工修订历史。
- `GET /api/ocr/statistics`：汇总成功、失败、待复核和修订数量。
- `POST /api/ocr/evaluations`：使用即时提交的脱敏真值，按 `HIGH`、`MEDIUM`、`LOW` 清晰度计算字段准确率、检出率、失败率和平均处理耗时；真值不持久化。

每个任务包含 `sourceFile.sha256`、`engineVersion`、`processingDurationMs`、`textBlocks` 和可选 `fields`。业务侧保存的版本关系至少应记录 `taskId`、档案版本 ID、确认人、确认时间和发布结果；失败任务保留原图与 `errorMessage`，业务流程可改为人工录入而不应中断。

前文关于“没有人工修订接口”的首期说明已被此处的当前实现替代：OCR 仍会直接返回结果，但人事人员可以通过字段修订接口完成复核，并保留修订前后值、操作者、原因和时间。

OCR 任务还保留 `detectionPreview` 派生证据。该 PNG 与原图分开保存，保持原图尺寸和坐标参考系，在文本检测框上绘制序号、置信度和识别文本，并通过 `GET /api/ocr/tasks/{taskId}/detection-preview` 提供下载。它用于人工复核和定位漏检、碎片化检测框、低置信度识别等问题，不能替代原始上传文件。原图和效果图统一写入 MinIO，SQLite 只保存任务元数据与内部对象引用；历史本地图片通过迁移工具上传校验后清理。

## 2026-09-17 当前技术方案：核心微服务与读写分离

### 1. 方案结论

采用“Vue 管理端 + Spring Boot 核心业务微服务 + 独立 Python OCR 服务 + MySQL 主从读写分离 + Redis 缓存”的架构。微服务只按核心业务边界拆分，不把每张表或每个小功能单独拆成服务：网关、身份与组织、档案与 OCR 对接、人事流程四个 Java 服务，加上已经完成的 `ocr-service`，共五个运行单元。

三类业务数据库使用同一组 MySQL 主库/只读副本：`identity_db` 保存身份、权限和组织；`archive_db` 保存员工、档案、文件和 OCR 业务关联；`workflow_db` 保存申请、审批、使用、盘点和流程。服务只通过 API 和业务 ID 交互，不跨库查询、不建立跨库物理外键。这样既满足微服务的数据隔离，又避免过细拆分带来的部署和事务复杂度。

### 2. 技术选型

| 类别 | 选择 | 采用理由 |
|------|------|----------|
| 前端 | Vue 3 + Vite + Element Plus + Pinia + Axios + ECharts | 适合权限菜单、表单、表格、审批和统计页面 |
| 网关 | Spring Cloud Gateway | 统一路由、CORS、traceId、JWT 初步校验和限流入口 |
| 业务后端 | Java 17 + Spring Boot 3.x + Spring Security + MyBatis | Java 17 LTS 在当前开发环境可用，事务、权限、参数校验和 MySQL 业务生态成熟；使用原生 MyBatis，SQL 可审查 |
| 服务间调用 | Spring Cloud OpenFeign 或 WebClient | 对身份、档案、流程和 OCR 调用提供明确 HTTP 契约；首期使用同步调用 |
| 数据库 | MySQL 8.0，InnoDB | 适合关系模型、事务、分页、索引和版本历史 |
| 读写路由 | `AbstractRoutingDataSource` + `@Transactional(readOnly = true)` | 由事务只读属性选择主库或只读副本，避免业务代码到处判断数据源 |
| 缓存 | Redis 7 | 会话、权限、字典、列表摘要、幂等键和短时锁；不作为业务事实库 |
| 文件存储 | MinIO（开发/演示）或兼容 S3 的对象存储 | 原图、检测框 PNG 和导出文件不进入 MySQL 大字段 |
| OCR | 现有 Python 3.10+ + FastAPI + PaddleOCR | 保留已验证的文本识别、检测框、字段抽取和修订接口 |
| 文档接口 | Springdoc OpenAPI + FastAPI OpenAPI | 便于前后端联调、论文展示和接口验收 |

### 3. 微服务边界

| 服务 | 数据归属 | 主要职责 | 不负责的内容 |
|------|----------|----------|--------------|
| `gateway-service` | 无业务库 | 统一入口、路由、CORS、traceId、限流、JWT 初步校验 | 不写员工或档案业务数据 |
| `identity-service` | `identity_db` | 登录、用户、角色、权限、部门、岗位、JWT、数据范围 | 不保存档案文件和 OCR 结果 |
| `archive-service` | `archive_db` | 员工、档案主记录、材料、文件元数据、版本、OCR 绑定、字段确认、档案查询 | 不审批人事申请，不直接读 OCR SQLite |
| `workflow-service` | `workflow_db` | 入职/调动/离职、访问/借用、审批、使用归还、盘点和异常 | 不复制员工主数据，不保存原图 |
| `ocr-service` | 现有 SQLite + 文件目录，后续可替换存储 | 图像预处理、文字检测识别、文本块、字段映射、检测框效果图和修订历史 | 不修改员工、档案版本和审批状态 |

服务间关联规则：`employeeId`、`archiveId`、`archiveVersionId`、`ocrTaskId` 和 `requestId` 均为逻辑引用。调用方必须通过对方服务验证对象是否存在及是否有权限，禁止在本地复制一份可被当作事实来源的员工或档案状态。

### 4. 总体调用链

```text
Vue 3
  -> gateway-service
     -> identity-service       -> identity_db 主库/只读副本
     -> archive-service        -> archive_db 主库/只读副本
          |                    -> MinIO
          `--------------------> ocr-service -> OCR 文件目录/SQLite
     -> workflow-service       -> workflow_db 主库/只读副本
          |                    `-> identity/archive API 校验业务 ID
     `-> Redis（会话、权限、缓存、幂等）
```

写操作从网关进入业务服务后必须在主库事务中完成；只读查询默认进入只读副本。文件上传先由档案服务完成类型、大小、哈希和权限校验，再写入 MinIO，并把文件内容转发给 OCR 服务。OCR 返回的 `taskId`、状态、检测框地址和字段结果摘要写入档案库；完整原始证据仍由 OCR 服务保留。

### 5. MySQL 读写分离设计

#### 5.1 物理拓扑

```text
identity/archive/workflow service
       |                         |
       | write                   | read-only
       v                         v
MySQL primary  ------------->  MySQL replica
       \\                        /
        \\---- Redis cache ----/
```

实际部署使用一主一从异步复制。三个逻辑数据库位于同一主从集群，服务通过环境变量分别配置 `MYSQL_WRITE_URL` 和 `MYSQL_READ_URL`。开发机可以先启动主库和副本两个 MySQL 实例；若资源不足，使用同一实例的两个连接地址模拟路由，但演示文档必须明确这是路由验证而非真实复制。

#### 5.2 路由规则

- 新增、修改、删除、状态流转、审批和版本发布：主库。
- `@Transactional(readOnly = true)` 的列表、详情和统计查询：副本。
- 写事务中的后续查询、刚发布版本的详情、审批成功后的状态确认：强制主库，满足读己之写。
- 副本不可用或延迟超过阈值时：查询可降级主库并写入告警；写入不切换到副本。
- 事务提交后才删除或刷新 Redis 缓存，避免回滚后缓存出现错误状态。

#### 5.3 实现约束

数据源路由放在公共 starter 中，业务 Mapper 不感知 JDBC URL。读路由通过事务只读属性和显式 `@UsePrimary` 注解控制。分页排序字段只允许后端白名单，所有关联字段建立组合索引，避免因为副本查询而放大慢 SQL。主从复制延迟、连接池、命中率和降级次数纳入健康指标。

### 6. Redis 缓存设计

| Key 模式 | 内容 | TTL/失效策略 |
|----------|------|-------------|
| `hr:session:{jti}` | JWT 黑名单或会话状态 | 按 token 剩余有效期 |
| `hr:perm:user:{userId}` | 用户角色、权限编码和数据范围摘要 | 30 分钟；角色/权限变更主动删除 |
| `hr:org:department:tree` | 部门树摘要 | 10 分钟；部门变更主动删除 |
| `hr:dict:{type}` | 状态、材料类型和字典项 | 1 小时；后台修改主动删除 |
| `hr:list:archive:{hash}` | 已脱敏的档案列表摘要 | 60 秒；档案写入后按业务前缀删除 |
| `hr:todo:user:{userId}:{sha256(scopeKey)}` | 当前授权范围内的待审批/待归还/OCR 失败摘要 | 30 秒；按用户和 scope 隔离，过期后回源 |
| `hr:idempotent:{requestId}` | 上传、审批和归还请求幂等结果 | 10 分钟；完成后保留到过期 |
| `hr:lock:{resourceType}:{resourceId}` | 档案版本发布、归还等短时互斥锁 | 不超过 30 秒，必须设置过期 |

缓存穿透使用参数校验和短时空值缓存，缓存击穿使用短锁，缓存雪崩使用 TTL 抖动。Redis 不保存身份证原图、完整 OCR JSON、检测框 PNG、文件二进制和不可重建的业务事实。

### 7. OCR 对接设计

档案服务对前端暴露统一的业务接口，前端不需要知道 OCR 的内部地址：

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/archive/employees/{employeeId}/documents` | `POST` | 上传材料、创建文件对象和档案版本 |
| `/api/archive/versions/{versionId}/ocr` | `POST` | 档案服务转发图片至 OCR，保存 `ocrTaskId` 关联 |
| `/api/archive/versions/{versionId}/ocr-result` | `GET` | 聚合档案版本、OCR 任务状态和字段结果 |
| `/api/archive/ocr-bindings/{bindingId}/detection-preview` | `GET` | 代理获取 OCR 检测框效果图 |
| `/api/archive/ocr-bindings/{bindingId}/fields/{fieldCode}` | `PUT` | 校验权限后调用 OCR 修订接口并保存业务确认记录 |
| `/api/archive/ocr-bindings/{bindingId}/publish` | `POST` | 人工确认后把允许发布的字段写入业务对象并记录版本 |

内部调用 OCR 时设置超时、请求 traceId 和最大文件大小。OCR 识别失败时档案版本仍为可人工处理状态，保存 `FAILED` 和错误信息；检测框效果图不存在时返回独立业务错误 `DETECTION_PREVIEW_NOT_FOUND`，不覆盖任务识别状态。对历史任务先调用查询接口，再按需请求效果图，利用 OCR 服务的自动补生成能力。

OCR 结果发布采用三层值：`ocr_value` 为原始字段值，`confirmed_value` 为人工修订值，业务主表字段为最终发布值。任何发布都必须记录操作者、时间、来源 OCR 任务和档案版本。

### 8. 数据库设计

#### 8.1 统一规范

- MySQL 8.0、`utf8mb4`、InnoDB；表名和字段名使用 `snake_case`。
- 主键使用 `BIGINT UNSIGNED`，由业务库本地生成或雪花算法生成；跨服务只传业务 ID，不共享自增序列。
- 所有核心表包含 `created_at`、`updated_at`；需要撤销的数据使用 `deleted_at` 或状态，不物理删除历史事实。
- 状态字段使用 `VARCHAR` 保存业务枚举，避免数据库 ENUM 造成服务版本耦合；应用层负责状态机校验。
- 不设置跨库物理外键；同库内的强一致关系由 MyBatis 事务和应用约束维护，便于主从复制、数据初始化和服务独立部署。
- 个人敏感字段采用应用层加密或脱敏存储；列表接口默认不返回完整身份证号和原始文件路径。

### 9. 接口约定

所有网关业务接口统一返回：

```json
{
  "code": "0",
  "message": "OK",
  "data": {},
  "traceId": "..."
}
```

错误码至少包括 `AUTH_REQUIRED`、`FORBIDDEN`、`VALIDATION_ERROR`、`RESOURCE_NOT_FOUND`、`STATE_NOT_ALLOWED`、`DUPLICATE_REQUEST`、`FILE_TYPE_NOT_SUPPORTED`、`OCR_FAILED`、`DETECTION_PREVIEW_NOT_FOUND` 和 `SERVICE_UNAVAILABLE`。GET 查询不因为 Redis 未命中而报错，写入接口使用 `Idempotency-Key` 或业务请求号防止重复提交。

### 10. 状态机

- OCR：`PENDING -> PREPROCESSING -> RECOGNIZING -> SUCCEEDED/FAILED`。
- 档案版本：`DRAFT -> OCR_PROCESSING -> REVIEW_REQUIRED -> PUBLISHED -> SUPERSEDED/VOID`。
- 人事申请：`DRAFT -> SUBMITTED -> PENDING_DEPT_APPROVAL -> PENDING_HR_REVIEW -> APPROVED/REJECTED/CANCELLED -> COMPLETED`。
- 档案访问：`DRAFT -> SUBMITTED -> PENDING_APPROVAL -> APPROVED/REJECTED -> IN_USE -> RETURNED/OVERDUE/ABNORMAL`。
- 盘点：`DRAFT -> IN_PROGRESS -> PENDING_HANDLE -> COMPLETED/CANCELLED`。

状态迁移由后端状态机、角色和数据范围同时校验。每次迁移在同一主库事务中写入业务表和操作日志；重复请求通过幂等键返回原结果。

### 11. 分阶段交付

1. 基础设施与工程骨架：网关、配置、统一响应、JWT、MySQL 主从连接、Redis、对象存储和链路标识。
2. 身份与组织：用户、角色、权限、部门、岗位、登录和菜单权限。
3. 档案 OCR 闭环：员工、档案、文件、版本、OCR 调用、检测框预览、字段修订和发布。
4. 人事与档案使用闭环：入职/调动/离职、访问/借用、审批、领取、归还和异常。
5. 盘点、统计与审计：盘点任务、差异处理、聚合统计、权限范围和完整测试。
6. P1 扩展：合同、批量导入导出、提醒和更丰富的统计。

每个阶段都必须先有接口/数据库测试，再进入下一阶段；代码实现前先审核本方案和对应实施计划。需求、架构、数据库设计和图表属于编码前的审核产物；审核通过后，按阶段实施计划创建对应的 Spring Boot 或 Vue 源文件。

### 12. 主要风险与应对

| 风险 | 应对 |
|------|------|
| MySQL 副本延迟导致刚写数据不可见 | 写事务后强制主库读取；监控延迟，必要时查询降级主库 |
| OCR 服务超时或检测框效果图缺失 | 保存原图和失败状态；预览使用独立错误码；允许重新请求和人工录入 |
| 服务拆分导致跨服务事务复杂 | 首期只使用同步 HTTP + 明确状态补偿，不做跨库事务；每个服务拥有自己的事实数据 |
| Redis 缓存与主库不一致 | 缓存只做加速；主库提交后失效，读取不到时从数据库重建 |
| 档案原图泄露 | 对象存储私有桶、短时下载地址、接口级权限校验和下载审计 |
| 需求范围过大 | P0 按上述六个阶段交付，合同、批量导入和消息推送放到 P1 |

## 2026-09-17 方案审核结论

本文档早期章节中的“模块化单体”和“Redis 初期不强制引入”属于 2026-09-16 的历史方案，不再作为当前实现依据。自本节起，以“核心微服务与读写分离”章节、`docs/数据库设计.md` 和 `docs/superpowers/plans/2026-09-17-platform-development.md` 为有效基线。

有效架构为：`gateway-service`、`identity-service`、`archive-service`、`workflow-service` 四个核心 Java 服务，加上独立 `ocr-service`；业务服务各自拥有 `identity_db`、`archive_db`、`workflow_db`，通过 MySQL 主库/只读副本和公共路由组件实现读写分离，Redis 作为缓存和幂等/锁中间件，Vue 3 管理端只访问网关。

当前开发顺序为“文档审核 -> Redis 业务缓存 -> Vue 核心工作台 -> workflow-service 流程闭环 -> 统计、盘点和数据范围权限 -> P1 扩展”。任何新增接口必须先补对应需求、数据库或契约说明和失败测试。

## 2026-09-20 方案实现校准

当前源码和运行验收以本节为准：

- OCR 核心能力已经落地为同步 HTTP 接口：上传图片后返回文本块、置信度和原图坐标；原图和检测框 PNG 均持久化在 OCR 服务数据目录，MySQL 只保存档案侧的任务关联和预览摘要。
- 检测框效果图保留原图视觉内容，并绘制序号、置信度和识别文本。效果图缺失时不覆盖文字识别结果；OCR 服务会在原图和文本块存在时自动补生成历史预览，无法补生成时返回 `DETECTION_PREVIEW_NOT_FOUND`。
- workflow-service 不跨库访问 archive/identity 表。资源授权通过 archive-service 内部 HTTP API 使用原 JWT 完成，workflow_db V4 保存申请目标部门以及盘点明细的员工/部门快照，查询和状态变更均使用 JWT 的 `DataScope`。
- 当前本地验收运行五个服务：`gateway-service`、`identity-service`、`archive-service`、`workflow-service` 和 `ocr-service`；数据库、Redis、MinIO 为基础设施，前端只访问网关。

## 2026-09-20 当前开发规格与接口契约

当前开发以 `docs/superpowers/specs/2026-09-20-microservice-data-contract-design.md` 为准。有效服务边界、主从路由、Redis key 与 TTL、OCR 内外部接口、错误码、状态机和测试门槛均以该规格为准；本文件早期章节中关于模块化单体、OCR 人工确认边界或未落地接口的描述仅保留为历史记录，不得作为新增代码依据。
