# OCR 识别实验报告（第 6 章实验素材）

> 版本：v1.0 ｜ 日期：2026-10-13 ｜ 样本种子：20261013
> 前期工作：[`docs/ocr-clarity-evaluation.md`](../ocr-clarity-evaluation.md)（2026-10-11，36 张单版式派生样本，仅覆盖姓名 + 员工编号两字段）。本报告在其基础上把样本集升级为多版式、多退化、指标完整的可复算实验。

## 1. 实验目的与环境

**目的**：定量评估本平台 OCR 管线在不同版式、不同成像清晰度与退化扰动下的字段识别能力，并据此回答两个工程问题：

1. 字段准确率、检出率随清晰度下降如何衰减；
2. 置信度阈值如何决定「需要人工复核」的工作量（低置信度召回率与人工修订率的取舍）。

**运行环境与引擎说明**：

| 项目 | 取值 |
| --- | --- |
| 操作系统 | macOS（本地开发机） |
| Python | 3.14，Pillow 12.3 |
| OCR 引擎 | **本轮报告数字来自 `mock` 引擎基线**（`OCR_ENGINE=mock` / `OCR_MOCK=1`） |
| 真实引擎 | 项目正式引擎为 PaddleOCR（`paddleocr`，项目固定 PaddlePaddle 3.3.0），但本机未安装 Paddle 模型权重 |
| 评测方式 | 脚本化离线评测，不混入 `ocr-service/tests/` 的 62 项 pytest |

> **重要声明**：下表所有指标数字均为 **mock 引擎基线**。mock 引擎不做真实推理，而是以 ground truth 为底、按清晰度施加**确定性噪声模型**（字段漏检、形近字误识 0/O·1/l·5/S、字段串扰、格式位数错误、置信度抖动），用于验证「样本生成 → OCR 调用 → 字段级判定 → 指标汇总」整条评测管道可复跑。**真实 PaddleOCR 结果待本地安装模型后用同一命令补跑**，不得把 mock 数字表述为生产准确率。

## 2. 样本集构成

样本由 `scripts/generate-ocr-samples.py` 用 PIL 程序化渲染，无任何手工图像处理。

| 维度 | 取值 |
| --- | --- |
| 版式数 | 4（身份证正面 / 员工入职登记表 / 简历摘要页 / 劳动合同首页） |
| 清晰度档 | 3（high 原始渲染 / medium 轻模糊+JPEG q75 / low 强模糊+亮度×0.7+对比度×0.8+JPEG q50） |
| 每格化名数 | 3（4 版式 × 3 清晰度 × 3 = **36 张基础样本**） |
| 字段总数 | 每张 5–8 个字段，全集合计 225 个期望字段 |
| 退化扰动 | 36 张中 4 张 ±10° 旋转、9 张半透明阴影、9 张单字段遮挡，其余 27 张无额外扰动 |
| 图像格式 | high 档导出 PNG，medium/low 档导出 JPEG |

**脱敏声明**：所有姓名（张三甲 / 李四乙 / 王五福 / 赵六丁）、身份证号（110101199001011234 等明显测试号段）、手机号（13800138000 系列）、邮箱（`@example.test`）、地址（示范路/样板路）均为写死的合成化名，**不含任何真实个人信息**。

**脚本位置**：
- 样本生成：`scripts/generate-ocr-samples.py`
- 评测脚本：`scripts/evaluate-ocr-experiment.py`
- 样本与真值：`scripts/samples/`（PNG 已 gitignore，ground-truth JSON 入库）
- 原始评测输出：`scripts/experiment-results/run-<timestamp>.json`

## 3. 标注规则

- **字段白名单**：每个版式固定字段编码（如 `idcard_front` 的 `name/gender/ethnicity/birth_date/address/id_number`），真值取自生成时写死的化名值，遮挡只盖图像、不改真值。
- **ground truth JSON schema**：
  ```json
  {
    "sample_id": "idcard_front_high_001",
    "layout": "idcard_front",
    "degradation": {"clarity": "high", "rotate_deg": 0, "shadow": false,
                     "occlusion": true, "occluded_field": "birth_date"},
    "fields": {"name": "李四乙", "id_number": "310104198505056789"},
    "source": "synthetic",
    "image_file": "png/idcard_front_high_001.png",
    "hash": "<sha256 of rendered bytes>"
  }
  ```
- **哈希校验**：每张图像字节计算 SHA-256 写入真值；评测时重新计算并比对（本轮 36/36 校验一致，`hash_ok=true`），保证评测的就是当时渲染的那张图。

## 4. 指标定义表

| # | 指标 | 定义 |
| --- | --- | --- |
| 1 | 字段检出率 | OCR 返回了该字段编码的期望字段数 ÷ 期望字段总数 |
| 2 | 字段准确率 | strip 后 OCR 值与真值**完全一致**的字段数 ÷ 期望字段总数 |
| 3 | 字段编辑距离准确率 | 归一化 Levenshtein ≥ 0.9 的字段数 ÷ 期望字段总数（容忍形近字一两位误差） |
| 4 | 失败率 | 任务状态 FAILED / 超时 / 返回空的样本数 ÷ 样本总数 |
| 5 | 错误分类 | ① `char` 字符误识（检出但编辑距离 0.5–0.9，如 0/O、1/l）；② `mapping` 字段映射错误（值落到了别的字段，编辑距离 <0.5）；③ `format` 格式校验失败（身份证位数/字符集、手机号位数、邮箱缺 @、工号格式不对）；另统计 `missed` 未检出 |
| 6 | 置信度分层准确率 | 检出字段按置信度分箱 ≥0.9 / 0.7–0.9 / <0.7，每箱内报字段准确率 |
| 7 | 低置信度正确召回率 | 真值正确但 OCR 置信度 <0.7 的字段数 ÷ 全部正确字段数（即「本来对、却被打回要求人工看」的比例） |
| 8 | 人工修订率 | 至少有一个字段与真值不完全一致的成功样本数 ÷ 成功样本数 |
| 9 | P50 / P95 延迟 | 单样本 OCR 端到端耗时（mock 下为模拟推理耗时分布）的中位数与 95 分位 |

## 5. 主结果表

### 5.1 按清晰度汇总（mock 引擎基线，n=36）

| 清晰度 | 样本 | 期望字段 | 检出率 | 字段准确率 | 编辑距离准确率 | 失败率 | 人工修订率 | P50 (ms) | P95 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| high | 12 | 75 | 0.907 | **0.853** | 0.880 | 0.083 | 0.364 | 1565 | 1722 |
| medium | 12 | 75 | 0.787 | **0.613** | 0.667 | 0.083 | 0.818 | 1173 | 1345 |
| low | 12 | 75 | 0.733 | **0.507** | 0.587 | 0.083 | 1.000 | 783 | 931 |

趋势（mock 噪声模型下）：字段准确率随清晰度单调下降 high→medium→low（85.3% → 61.3% → 50.7%），检出率同步下降（90.7% → 78.7% → 73.3%），人工修订率则反向上升（36% → 82% → 100%）。编辑距离准确率始终比「完全一致」高 4–8 个百分点，说明形近字（0/O、1/l、掉一个尾字）是主要误差来源。

### 5.2 按版式 × 清晰度的字段准确率

| 版式 | high | medium | low |
| --- | ---: | ---: | ---: |
| idcard_front | 0.556 | 0.556 | 0.444 |
| onboarding_form | 0.917 | 0.458 | 0.583 |
| resume_summary | 1.000 | 0.667 | 0.400 |
| contract_first_page | 0.944 | 0.833 | 0.556 |

> 每格仅 3 张样本，单格数字受个别失败/遮挡样本影响较大（如 `idcard_front_high_001` 整任务失败，把身份证 high 格拉低）；跨格看低清晰度组整体走低的方向是稳定的。正式结论应以更大样本量 + 真实 PaddleOCR 复核为准。

### 5.3 错误分类汇总（全集合计 77 个字段级问题）

| 错误类型 | 计数 | 占比 |
| --- | ---: | ---: |
| ① 字符误识 char | 24 | 31% |
| ② 字段映射错误 mapping | 7 | 9% |
| ③ 格式校验失败 format | 3 | 4% |
| 未检出 missed | 43 | 56% |

「未检出」占比最高，且主要集中在 low 档与被遮挡字段——这与真实 OCR 中「低质量图先在检测阶段丢框」的经验一致；字符误识次之；格式错误最少但危害最大（身份证号错一位仍可能通过初筛）。

## 6. 置信度分层与人工修订工作量分析

| 清晰度 | ≥0.9 箱（字段数 / 准确率） | 0.7–0.9 箱 | <0.7 箱 | 低置信度正确召回率 |
| --- | --- | --- | --- | --- |
| high | 57 / **98.3%** | 11 / 72.7% | 0 / — | 0.0% |
| medium | 5 / 100% | 44 / 86.4% | 10 / 30.0% | 6.5% |
| low | 2 / 100% | 8 / 87.5% | 45 / 64.4% | **76.3%** |

**阈值取舍结论**：
- 在 **high 档**，几乎所有字段置信度 ≥0.9 且该箱准确率 98.3%，把阈值定在 0.7 时几乎不会误报，人工修订率仅 36%。
- 在 **low 档**，55 个检出字段里有 45 个落进 <0.7 箱；但其中 64.4% 其实识别正确，导致 **76.3% 的正确字段被打回要求人工复核**——若直接用 <0.7 作为「必须人工」的红线，低清晰度材料的复核工作量被严重放大。
- 工程含义：固定 0.7 阈值对高质量件友好、对低质量件过保守。更合理的做法是把「置信度 <0.7」与「格式校验失败」「字段未检出」**并联**触发人工复核，而不是单看置信度；对低清晰度批次应整体走人工通道而非逐字段打回。

## 8. 结论与局限

**结论（mock 基线层面）**：
1. 评测管道（生成 → 调用 → 字段判定 → 9 类指标 → 失败清单）已端到端跑通并可一条命令复现。
2. 字段准确率、检出率随清晰度下降单调衰减，人工修订率反向上升，方向符合预期。
3. 置信度阈值对低清晰度批次的人工复核工作量影响极大（low 档 76.3% 的正确字段被低置信度打回），应与格式校验、字段缺失并联触发人工复核。
4. 错误以「字段未检出」和「形近字符误识」为主，格式类错误占比虽小但需硬校验兜底。

**局限（不可外推）**：
- 以上数字来自 **mock 噪声模型**，不是 PaddleOCR 真实识别结果，**不能外推到真实扫描件**。
- 样本全部由 PIL 渲染、白底正排、固定字体；未覆盖真实拍摄的透视畸变、复杂印章、手写体、阴影纹理、多栏表格与真实证件防伪底纹。
- 每格仅 3 张样本，统计置信区间宽，单格数字噪声大。
- 真实泛化结论需在安装 PaddleOCR 后、补充真实脱敏扫描件与人工双标真值时重跑。

## 9. 复现命令

```bash
# 1) 生成 36 张脱敏合成样本（PNG + ground truth JSON）
python scripts/generate-ocr-samples.py --personas 3

# 2) 用本地 mock 引擎跑通评测管道（不依赖 PaddleOCR）
OCR_MOCK=1 python scripts/evaluate-ocr-experiment.py

# 3) 若本机已启动 PaddleOCR 服务（默认 127.0.0.1:8000），去掉 mock 即跑真实推理：
python scripts/evaluate-ocr-experiment.py --base-url http://127.0.0.1:8000
```

原始逐样本判定输出落盘于 `scripts/experiment-results/run-<timestamp>.json`；样本真值在 `scripts/samples/ground-truth/`，图像字节在 `scripts/samples/png/`（gitignore）。
